# VMPing 可行性调研

> 版本：v1（2026-11-02）｜作者：ping-research（调研员）
> 对象：`/root/VMPing-mod`（Fabric 客户端模组，MC 26.3 / Loader 0.20.1 / Java 25 / Loom 1.18.4）
> 目标功能：**服务器不装 mod、只装客户端 mod，同服玩家也能看见彼此的标点**
>
> 本文所有结论都带证据（文件 + 行号 + 代码/签名）。证据来源只有四类：
> ① Loom 缓存的 **MC 26.3 官方名 jar**（`minecraft-common-deobf` / `minecraft-clientonly-deobf`，用 `javap` 反汇编）；
> ② **Fabric API 0.165.0+26.3 的模块 jar**（同样 `javap`）；
> ③ 上游 Ping Wheel `ref-26.3`（v1.12.2）源码；
> ④ VMFashion / vmtools-next 后端源码。
> 凡是"凭记忆"的地方都标了 ⚠️ 并给出复核方法。

## 0. 结论速览（TL;DR）

| 编号 | 结论 | 证据位置 |
|---|---|---|
| K1 | **原版服务端对客户端自定义载荷是"解码后丢弃"，没有任何转发**：`ServerboundCustomPayloadPacket` 只认识 `minecraft:brand` 一种，其余走 `DiscardedPayload`；即使 `minecraft:brand` 到了游戏阶段，`ServerGamePacketListenerImpl#handleCustomPayload` 是**空方法**（字节码只有 `return`） | §A.1 / §A.2 |
| K2 | 因此"客户端↔客户端"**不存在任何原版通道**，必须有服务器之外的第三方中继（HTTP/WS/第三方服务都算中继） | §A.6 |
| K3 | 上游 Ping Wheel 是 **multiloader 双端 mod**（`environment: "*"` + `main` 入口点），它在原版服上是**静默失效**的（`ClientPlayNetworking.canSend()` 为 false 直接 return）——这正好反证了"必须有服务端" | §A.5 / §D.1 |
| K4 | **选定方案 A：自建 HTTP 中继**（复用 VMFashion 的 MC 账号认证 + Bearer token + 后端 `vmtools-next`）。改动面最小、无需服务器配合、延迟可控（长轮询 20s，事件唤醒后 <300ms 量级） | §B |
| K5 | **MC 26.3 已经没有 `WorldRenderEvents`**：`fabric-rendering-v1` 从 26.1 起就删掉了 `net/fabricmc/fabric/api/client/rendering/v1/world/*`，26.3 的替代品是 `SubmitRenderPhases` 提交式管线。**上游 26.3 版本根本不做世界空间渲染**，它把世界坐标投影到屏幕后用 `GuiGraphicsExtractor` 画 2D——这是我们必须照抄的关键结论 | §E.1 |
| K6 | 协议 v1 在 MC 26.3 + 现有后端能力下**基本可实现**，但有 **8 条需要补齐/修正**（token audience、自己标点回显去重、时钟偏移、离线账号、轮询并发上限等），逐条见 `实现方案.md §12` | `实现方案.md §12` |

## A. 为什么 vanilla 服务端不行（证据链）

### A.1 证据链①：服务端只认识 `minecraft:brand`，其余载荷"读掉就扔"

### A.2 证据链②：即使载荷被识别，游戏阶段的处理器是**空方法**

**来源**：同一 jar → `net/minecraft/server/network/ServerGamePacketListenerImpl.class`

```text
  public void handleCustomPayload(net.minecraft.network.protocol.common.ServerboundCustomPayloadPacket);
    Code:
         0: return
```

（`javap -p -c` 全量输出第 6704–6706 行；该方法在 131 KB 的类里只有 1 条指令。）

对比**配置阶段**的 `ServerCommonPacketListenerImpl`：

```text
  public void handleCustomPayload(net.minecraft.network.protocol.common.ServerboundCustomPayloadPacket);
    Code:
         0: return
```

**两处都是 `return`**。也就是说：原版服务端从协议层到逻辑层，**没有任何一处**会读取自定义载荷的语义，更没有"广播给其他玩家"的代码路径。

包的分发链（`ServerboundCustomPayloadPacket#handle`）本身就只是把 `this` 交给 listener：

```text
  public void handle(net.minecraft.network.protocol.common.ServerCommonPacketListener);
    Code:
         0: aload_1
         1: aload_0
         2: invokeinterface #23, 2  // InterfaceMethod ...ServerCommonPacketListener.handleCustomPayload:(...ServerboundCustomPayloadPacket;)V
         7: return
```

**结论**：`ServerboundCustomPayloadPacket` 在原版服务端是**死胡同**。

### A.3 证据链③：反方向（服务端→客户端）必须由服务端主动 `send`

客户端能收到 `ClientboundCustomPayloadPacket` 的前提，是**服务端进程里有代码去构造并发送它**。原版服务端只发 `minecraft:brand`（登录时）等极少数固定载荷，没有任何"转发别的玩家的自定义载荷"的逻辑。

因此"让 B 看见 A 的标点"在原版服上无解：**A 的载荷到不了服务端逻辑层，服务端也没有任何把它发给 B 的代码**。

### A.4 证据链④：Fabric 自己的 API 就是按"服务端也要装 mod"设计的

**来源**：`fabric-networking-api-v1-6.4.0+a21c9eb65d.jar`（26.3 对应版本，见 `fabric-api-0.165.0+26.3.pom`）

```java
public final class net.fabricmc.fabric.api.client.networking.v1.ClientPlayNetworking {
  public static boolean canSend(net.minecraft.resources.Identifier) throws IllegalArgumentException;
  public static boolean canSend(net.minecraft.network.protocol.common.custom.CustomPacketPayload$Type<?>);
  public static <T extends CustomPacketPayload> boolean registerGlobalReceiver(CustomPacketPayload$Type<T>, PlayPayloadHandler<T>);
  public static void send(net.minecraft.network.protocol.common.custom.CustomPacketPayload);
  ...
}
```

`canSend(...)` 的语义是"**对端**是否注册了这个通道"（通道通过 `minecraft:register` 协商）。原版服务端不注册任何第三方通道 → `canSend` 恒为 `false`。

### A.5 证据链⑤：上游 Ping Wheel 在原版服上是"静默失效"

**来源**：`upstream/Minecraft-Ping-Wheel/fabric/src/main/java/nx/pingwheel/fabric/platform/PlatformNetworkServiceImpl.java:12-18`

```java

		if (!ClientPlayNetworking.canSend(packet.getId())) {
			return;                      // ← 原版服：直接 return，玩家按了没反应
```

而它的 mod 元数据要求**服务端也装**：

`upstream/Minecraft-Ping-Wheel/fabric/src/main/resources/fabric.mod.json`

```json

	"entrypoints": {
		"client": ["nx.pingwheel.fabric.FabricClient"],
		"main":   ["nx.pingwheel.fabric.FabricMain"],     // ← 服务端入口点
		...
	}
```

`common/.../core/ServerCore.java:88-99` 才是真正把标点广播出去的地方（`ServerPlayNetworking.send`）：


**这是最有力的反证**：一个专门做"标点"的成熟 mod，在原版服上**完全不能用**，作者的选择是"要求服务端也装"。

### A.6 排除法：为什么"借道原版通道"都不行

| 想借的通道 | 为什么不行 |
|---|---|
| 自定义载荷（custom payload） | 见 A.1/A.2：解码即丢弃 |
| 聊天 / `/me` / `/msg` | ① 服务端会把聊天广播给**所有**人（含不装 mod 的人），刷屏；② 需要玩家有发言权限（很多服禁言/限速/关键词过滤）；③ 位置信息以文本形式进入服务器日志与聊天记录，**隐私面更大**；④ 20 秒 TTL 的短命标点用聊天广播，语义完全错位 |
| 告示牌 / 物品展示框 / 盔甲架 | 要落地成方块实体 → 需要建造权限、会污染世界、TTL 无法自动回收、跨维度失效 |
| 记分板 / 统计数据 | 只能存整数，需要 OP 权限创建 objective；且**读**记分板需要服务端下发（`ClientboundSetObjectivePacket` 只在加入/变更时发），无法做高频事件流 |
| 服务器资源包 / MOTD | 单向、静态、由服主控制 |
| 客户端 `ClientPlayNetworking` 发到原版服 | 见 A.5 |

**唯一剩下的方向：服务器之外的中继。** 客户端把标点发到"我们自己的服务器"，其他客户端从那里拉。这就是协议 v1 的设计前提，也是 VMFashion 已经验证过的范式。

## B. 方案对比

评分维度：**可行性**（能否在 MC 26.3 客户端侧实现）、**延迟**、**部署成本**、**是否需要服务器配合**、**隐私面**。

### B.0 对比总表

| 方案 | 可行性 | 端到端延迟 | 部署成本 | 需服务器配合 | 隐私面 | 结论 |
|---|---|---|---|---|---|---|
| **A. 自建 HTTP 中继**（复用 VMFashion 后端） | ✅ 高（范式已验证） | 长轮询最坏 20s，事件唤醒典型 **0.1–0.5s**（见 §F.1） | 低：加 1 个 FastAPI 路由 + 内存房间表 | ❌ 不需要 | 中：服务端能看到玩家 UUID/坐标/房间 | **选定** |
| B. 服务端插件 / companion mod | ✅ 技术上最优（就是上游做法） | 极低（同 tick 广播，<50ms） | 高：Paper/Fabric/Forge/NeoForge 各一套 + 服主安装 + 审核 | ✅ **强依赖** | 低（数据不出服） | ❌ 违背本项目的核心前提 |
| C. 借道聊天 / 命令 / 告示牌 | ⚠️ 勉强（聊天可行但体验差） | 低 | 极低 | ❌（但要发言权限） | **高**：坐标进聊天记录/日志 | ❌ 否决（刷屏 + 权限 + 隐私） |
| D. 第三方服务（Discord/QQ bridge） | ⚠️ 可行但绕 | 高（1–5s，受第三方限速） | 中（要 bot + webhook + 中转） | ❌ | **很高**：数据出境到第三方平台 | ❌ 否决（延迟 + 隐私 + 依赖） |
| E. 原版机制（记分板/统计/告示牌） | ❌ 低 | — | — | ✅ | 中 | ❌ 否决（见 §A.6） |
| E'. 自建 WebSocket 长连接 | ✅ 高 | 低（<100ms） | 中（后端要常驻连接 + 反代升级） | ❌ | 中 | 🔶 备选（v2 演进方向） |

### B.1 方案 A：自建 HTTP 中继（选定）

**做法**：客户端 → `POST /api/ping/rooms/{roomId}/pings`；其他客户端 → `GET .../pings?since=N&timeout=20` 长轮询。

**为什么选它**：
1. **范式已验证**：VMFashion 已经用"MC 账号 serverId 挑战认证 → Bearer token → HTTP/JSON"跑在生产（`https://www.venusyu045.cn/api/fashion`），客户端代码可以直接搬。
2. **后端已存在**：`/workspace/VMTools-Web/vmtools-next/backend` 是现成的 FastAPI 服务，加一个 `api/routers/ping.py` + `core/ping_room.py` 即可，不用新起服务、不用新域名、不用新证书。
3. **零服务器配合**：这是本项目的**唯一硬约束**。
4. **延迟可接受**：标点不是竞技级同步，20s TTL 的东西，几百毫秒的额外延迟无感（见 §F.1 的量化）。

**代价**：
- 长轮询占连接：每玩家 1 条常驻 HTTP 连接（20s 一轮，空转时也是 1 请求/20s）。
- 服务端单 worker 约束（`backend/config/config.prod.yaml:5` 明确 `workers` 保持 1）→ 房间表可以放内存，但也意味着**不能水平扩容**（见 §F.5）。

### B.2 方案 B：服务端插件 / companion mod（否决）

技术上这是**最优解**（上游 Ping Wheel 就是这么做的，延迟 <50ms、数据不出服）。但：

- 违背需求原文"**服务器不装 mod**"。
- 工程上是 4 份代码（Paper 插件 / Fabric / Forge / NeoForge），上游 `buildSrc` + `forge` + `neoforge` + `fabric` 四套构建就是明证。
- 服主审核、版本跟随（每次 MC 大版本都要重发）、玩家还得去说服服主。

**结论**：不作为 v1 方案，但**保留接口**——`实现方案.md` 里把"传输层"抽象成 `PingTransport` 接口，将来若某个服主愿意装 companion mod，可以插一个 `ServerModTransport` 走原版通道，零延迟。

### B.3 方案 C：借道聊天 / 命令 / 告示牌（否决）

| 子方案 | 问题 |
|---|---|
| `/me` 或普通聊天发坐标 | ① 广播给所有人（含没装 mod 的），刷屏；② 需要发言权限（很多服新号禁言）；③ 坐标进服务器日志 + 聊天记录；④ 无法区分"标点"与"聊天"，客户端解析脆弱 |
| 私聊 `/msg` | 只能一对一，做不了"同服所有人可见" |
| 告示牌 / 展示框 | 要建造权限、污染世界、无法自动回收、跨维度失效 |
| 命令方块 / `/setblock` | 需要 OP |

**唯一有价值的变体**：**用聊天做"降级通道"**——当后端不可达且服里有 `!ping` 类自定义命令时，可选地把标点编码成短字符串发出去。**v1 不做**（解析脆弱、隐私差），列为 v2 可选项。

### B.4 方案 D：第三方服务（否决）

Discord/QQ 机器人 bridge：延迟 1–5s（受第三方 API 限速）、需要额外常驻 bot、**坐标数据出境到第三方平台**（隐私面最大）、且国内玩家访问 Discord 本身有门槛。

**结论**：否决。但要注意一个**反向用法**是合理的：**把标点转发到 QQ 群做"战报"**（低频、非实时），这是 v2 的运营功能，不是同步通道。

### B.5 方案 E'：WebSocket（备选，v2）

`vmtools-next` 已经跑着 `socket.io`（`main.py:589` `sio_app = socketio.ASGIApp(sio, other_asgi_app=app)`），理论上加一个 `/ping` namespace 就能做全双工推送，延迟 <100ms、连接数比长轮询省。

**为什么 v1 不做**：
1. 长轮询客户端代码量小得多（`HttpClient.sendAsync` 就够，不用引 WS 库）。
2. 现有 nginx `/api/` 段 `proxy_read_timeout 300s`（`backend/deploy/nginx/vmtools-next.conf:39`）对 20–25s 长轮询绰绰有余；而 WS 需要额外配 `Upgrade` 头（`/socket.io/` 段已经配了，但那是给 socket.io 的）。
3. 协议 v1 已经按 HTTP 写好，先跑通再演进。

**演进路径**：协议层把"拉取"抽象成 `PingSubscription`，v2 换 WS 时 `net/` 层换实现、`core/` 不动。

## C. VMFashion 通信栈拆解

> 目标：明确"VMPing 能直接复用什么、必须改什么"。VMFashion 是**同作者、同 MC 26.3、纯客户端**的成熟项目，它的通信栈就是我们的模板。

### C.1 认证三步流程（challenge → 会话服务器 join → verify）

**来源**：`/root/VMFashion-mod/src/client/java/com/venus/vmfashion/net/FashionAuth.java`

```
doAuthenticate()  L120-168
  ├─ 0) https 门禁（L121-127）：后端地址不是 https（非回环）→ 直接失败，不发凭据
  ├─ 1) 取当前 MC 会话（L128-151）：Minecraft.getInstance().getUser()
  │      → uuid / name / accessToken；accessToken 缺失 → no_token（离线账号）
  ├─ 2) api.challenge(uuid, name, authServer)                       L156
  │      → 后端生成一次性 serverId（TTL 120s，绑定来源 IP）
  ├─ 3) joinSession(authServer, accessToken, uuid, serverId)         L164 / L213-253
  │      POST {sessionServer}/session/minecraft/join
  │      body = {accessToken, selectedProfile(无横线 uuid), serverId}
  │      → 证明"这个 UUID 现在确实登录着"
  └─ 4) api.verify(uuid, name, authServer, serverId)                 L165
         → 后端反查 hasJoined?username=&serverId=，**比对 UUID**，一致才签发 token
```

**关键细节**：
- `selectedProfile` 必须**去掉横线**（`FashionAuth.java:225`：`uuid.toString().replace("-", "")`）。
- 皮肤站（authlib-injector）的 join 端点要加 `/sessionserver` 前缀（`FashionAuth.java:219-221`）：
  ```java
  String url = authServer == null || authServer.isBlank()
          ? MOJANG_SESSION_SERVER + "/session/minecraft/join"
          : stripTrailingSlash(authServer) + "/sessionserver/session/minecraft/join";
  ```
- 并发去重：`authenticate()` 用 `volatile CompletableFuture<Session> inFlight`（L110-118），同一时刻只有一次认证在飞。

**后端对应**：`backend/src/vmtools_next/core/fashion_auth.py`
- `create_challenge()` L312（TTL 默认 120s）
- `consume_challenge()` L352（一次性，消费即删）
- `verify_with_session_server()` L418（`hasJoined` + **UUID 比对** L470）
- `issue_token()` L513 / `decode_token()` L540

**VMPing 可直接复用**：整套流程，只改两处——
1. token 的 `aud`（见 §C.2 与 `实现方案.md §12.1`）；
2. 客户端把 `Session` 的 `apiBaseUrl` 绑定检查从 `/api/fashion` 换成 `/api/ping`。

### C.2 token 生命周期与落盘

### C.3 https 强制

三层防线：

1. **认证前**（`FashionAuth.java:121-127`）：后端 base 不是 https → `insecure_backend`，连认证都不做（因为 `/auth/verify` 的响应体里就是 token）。
2. **发 Bearer 前**（`FashionApi.java:291-316`）：
   ```java
   if (withAuth) {
       if (!PackDownloader.isSecureUrl(baseUrl)) {
           throw new ApiException(400, "insecure_backend", "后端地址不是 https，出于安全已停止发送登录凭据");
       }
       builder.header("Authorization", "Bearer " + current);
   }
   ```
   用 400 而不是 -1 是有意的：**400 不计入熔断、不触发重试**，否则会变成"每 5 秒认证一次"的死循环（注释 L306 写明了）。
3. **发 accessToken 前**（`FashionAuth.java:213-218` + `validateAuthServer` L306-330）：皮肤站地址只允许 https（本机回环允许 http），拒绝 userinfo/query/fragment。

**VMPing 直接复用**：三条防线 + `isSecureUrl` 的判定（`PackDownloader.isSecureUrl`）。

### C.4 重试 / 熔断

**来源**：`net/RetryPolicy.java`（279 行）+ `net/FashionApi.java:324-377`

| 参数 | 默认值 | 位置 |
|---|---|---|
| 最大尝试次数 | 3 | `RetryPolicy.java:30` |
| 基础退避 | 400 ms | L32 |
| 最大退避 | 8 000 ms | L34 |
| 抖动比例 | 0.5 | L36 |
| 熔断阈值（连续失败） | 5 | L38 |
| 熔断冷却 | 30 000 ms | L40 |
| `Retry-After` 上限 | 60 000 ms | L42 |

**两个正交的"要不要重试"判定**：
- `isRetryable(status, code)`（L125）：只对 5xx / 网络错误 / 特定码重试；
- `countsTowardBreaker(status, code)`（L138）：**4xx 不计入熔断**（否则一个坏请求就把整个后端拉黑）。

**写操作不重试**：`RetryMode.NONE`（`FashionApi.java:318-322`，`post`/`put` 一律 NONE），避免重复提交。

**熔断门禁**：每次请求前 `retryPolicy.tryAcquire(now)`（`FashionApi.java:335-339`），熔断中直接 `failedFuture(circuit_open)`，**不再打后端**。

**重试不阻塞线程**：用 `CompletableFuture.delayedExecutor(delay, MS)`（`FashionApi.java:374-376`），不是 `Thread.sleep`。

**VMPing 直接复用**：整个 `RetryPolicy` 类（纯逻辑、零 MC 依赖、已有单测 `RetryPolicyTest`）。**但长轮询要特殊处理**：长轮询"超时返回空数组"是正常路径，不是失败，不能计入熔断（见 `实现方案.md §12.4`）。

### C.5 异步线程模型

```
                    ┌──────────────── 渲染线程（主线程）────────────────┐
 按键 / tick ──────▶│ PingController.queuePing()                        │
                    │   ↓ 立即本地渲染（不等待网络）                     │
                    │ PingApi.postPing(...)  → 返回 CompletableFuture    │
                    └───────────────────┬───────────────────────────────┘
                                        │  HttpClient.sendAsync（JDK 线程池）
                                        ▼
                    ┌──────────── 后台线程（不碰 Minecraft 类）─────────┐
                    │  解析 JSON → 纯数据 record                        │
                    │  CompletableFuture 链式重试 / 熔断                 │
                    └───────────────────┬───────────────────────────────┘
                                        │  Minecraft.getInstance().execute(...)
                                        ▼
                    ┌──────────────── 回到主线程 ────────────────────────┐
                    │  更新 PingRepository（仅主线程读写）               │
                    └────────────────────────────────────────────────────┘
```

**铁律**（VMFashion 全程遵守，`SyncService.java` 1285 行里凡是改 Minecraft 状态的都在 `execute` 里）：
1. **网络线程绝不碰 `Minecraft` 的字段**（`level` / `player` / `connection` 都是主线程独占）。
2. **共享状态只在主线程读写**，跨线程用 `CompletableFuture` 回主线程（`Minecraft#execute(Runnable)`，`Minecraft extends ReentrantBlockableEventLoop<Runnable>` 所以有 `execute`）。
3. **渲染热路径零分配 / 零锁**：渲染时只读主线程维护的 `ArrayList`。
4. `HttpClient` 要显式 `close()`（`FashionApi.java:72`，`shutdownNow` 不等在飞请求），否则配置热重载会泄漏线程池。

**上游对照**：`PingManager.acceptPingPacket` 也是先做纯计算，再 `Game.execute(() -> {...})` 才动 `PING_REPO`（`PingManager.java:95-100`）。

#### D.2.1 `core/PingController.java`（84 行）——射线拾取 + 序列号纠偏

```java
// L36-50
public static void pollPingAction(float tickDelta) {
    if (!pingQueued || Game.level == null) return;
    var time = (int)Game.level.getGameTime();
    if (CLIENT_CONFIG.getCorrectionPeriod() < MAX_CORRECTION_PERIOD
            && time - lastPing > CLIENT_CONFIG.getCorrectionPeriod() * TPS) {
        ++pingSequence;                       // ← 序列号只在"距离上次标点超过纠偏周期"时自增
    }
    lastPing = time;
    pingQueued = false;
    performPingAction(tickDelta);
}
```

**设计要点**：
- **`pingQueued` 延迟到渲染帧执行**（`CommonClient.onRenderWorld` 里调 `pollPingAction(ctx.tickDelta)`，`CommonClient.java:66-69`）——因为射线拾取需要 `tickDelta` 的插值视线。
- **序列号（`pingSequence`）的语义**：同一个序列号的标点视为"同一个标点的修正"。客户端在 `correctionPeriod`（默认 1s）内重复按，会**复用同一个 sequence**，服务端/接收端用 `(authorId, sequence)` 做 key 覆盖（见 D.2.2）——这就是"按住中键快速挪动光标，标点跟着走"的效果。
- 超过 `correctionPeriod` 才 `++pingSequence` → 变成一个新标点。

**射线**（L59-82）：

#### E.1.3 上游 26.3 的做法：**根本不画世界空间几何**

`upstream/.../render/WorldRenderContext.java`（全文 13 行）：

```java

	public final Matrix4f modelViewMatrix;
	public final Matrix4f projectionMatrix;
	public final Float tickDelta;
	public final CameraRenderState camera;
}
```

它只是一个**矩阵容器**，不是 Fabric 的事件对象。渲染全部发生在 HUD：

- `MathUtils.worldToScreen(Vec3, ctx)`（`MathUtils.java:14-31`）：
  ```java
  var worldPosRel = new Vector4f(worldPos.subtract(ctx.camera.pos).toVector3f(), 1f);
  ctx.modelViewMatrix.transform(worldPosRel);
  ctx.projectionMatrix.transform(worldPosRel);
  var depth = worldPosRel.w;                 // ← w <= 0 表示在相机背后
  if (depth != 0) worldPosRel.div(depth);
  return new ScreenPos(window.getGuiScaledWidth()  * (0.5f + worldPosRel.x * 0.5f),
                       window.getGuiScaledHeight() * (0.5f - worldPosRel.y * 0.5f),
                       depth);
  ```
- 然后 `GuiGraphicsExtractor` 在 2D 上画图标/文字/箭头（`PingLocationRenderer` / `DirectionIndicatorRenderer`）。

**为什么这样更好**：
1. 标点是"UI 语义"而不是"世界几何"——不需要被方块遮挡、不需要深度测试、不需要光照；
2. 屏幕空间画法**只有一套矩阵运算**，跨版本稳定；
3. 26.3 的 submit 管线对"每帧要改的临时几何"并不友好（要构造 `SubmitNode` 实现类），成本远高于投影。

**我们的结论**：**照抄上游**——用 mixin 抓 `CameraRenderState` 的 `viewRotationMatrix` + `projectionMatrix`，投影到屏幕，在 HUD 里画。

⚠️ **`InputConstants.MOUSE_BUTTON_3` 在 26.3 不存在**（GLFW 命名 `MOUSE_BUTTON_1/2/3` 已被语义化命名取代）。中键用 `InputConstants.MOUSE_BUTTON_MIDDLE`。
（任务书里写的 `InputConstants.MOUSE_BUTTON_3` 需要更正。）

#### E.3.4 与 `keyPickItem`（选取方块）的冲突

**原版行为**（`Minecraft#handleKeybinds` 字节码，`javap -p -c` 输出）：
```text
     529: aload_0
     530: getfield   options:Lnet/minecraft/client/Options;
     533: getfield   Options.keyPickItem:Lnet/minecraft/client/KeyMapping;
     536: invokevirtual KeyMapping.consumeClick:()Z
     539: ifeq 647
     ...
     588: aload_0
     589: getfield   options:Lnet/minecraft/client/Options;
     592: getfield   Options.keyPickItem:Lnet/minecraft/client/KeyMapping;
     595: invokevirtual KeyMapping.consumeClick:()Z
     598: ifeq 608
     601: aload_0
     602: invokevirtual Minecraft.pickBlockOrEntity:()V
     605: goto 588
```

即：`Minecraft#handleKeybinds()`（private void）消费 `options.keyPickItem` 的点击并调用 `pickBlockOrEntity()`（private void）。

**方案对比**：

| 方案 | 做法 | 评价 |
|---|---|---|
| ① **改默认键**（上游做法） | 默认 `MOUSE_BUTTON_5`（侧键），玩家想用中键自己绑 | 零冲突，**推荐作为默认** |
| ② **抢点击 + 条件让行**（上游 `InputUtils.consumePingHotkey`，D.2.12） | 撞键时只在准星打空时 `consumeClick()` | 不需要 mixin，**推荐实现** |
| ③ mixin 抑制 | `@Inject(method="handleKeybinds", at=@At("HEAD"), cancellable=true)` 里判断"本 tick 已触发标点"→ `ci.cancel()`；或 `@Inject(method="pickBlockOrEntity", at=@At("HEAD"), cancellable=true)` 直接取消 | 能行但**没必要**，且 `ci.cancel()` 会顺带取消同一方法里的攻击/使用逻辑（`handleKeybinds` 里还有 `keyAttack`/`keyUse` 循环），风险大 |
| ④ 混合 | 默认中键 + 方案②让行 | **推荐**（体验最接近玩家直觉） |

**结论**：默认键用 `MOUSE_BUTTON_MIDDLE`，实现方案②。**v1 不写 mixin 处理按键**。

#### E.3.5 轮盘选型（按住中键 → 移动鼠标 → 松开）

上游是"按下即标点"（无轮盘）。协议 v1 §7.2 写的是"打开轮盘；移动鼠标选类型；松开"。实现要点：
- 按下：记录 `System.currentTimeMillis()` + 打开一个 `Screen`（或直接在 HUD 里画轮盘 + 监听鼠标位置）；
- 建议用**不暂停游戏的 Screen**（`isPauseScreen() → false`），否则多人游戏会卡住；
- 但 `Screen` 打开时鼠标会解锁（`MouseHandler` 释放光标），**轮盘期间无法转视角**——这是可接受的（标点场景就是停下来标记）；
- 松开：`mouseReleased(MouseButtonEvent, ...)` → 按角度分区算 `kind` → 关闭界面 → 标点。

**替代做法**（更轻）：不打开 Screen，直接在 `ClientTickEvents` 里检测 `KeyMapping.isDown()` 边沿 + 读 `minecraft.mouseHandler` 的光标位置画 HUD 轮盘。**v1 用 Screen**（简单、可靠、易做交互反馈），M3 里程碑验证后再考虑优化。

## F. 可行性与风险结论

### F.1 延迟量级

| 环节 | 量级 | 说明 |
|---|---|---|
| A 按键 → 本地渲染 | **0 ms**（同帧） | 本地立即画，不等网络（协议 v1 §7.2） |
| A → 后端（POST） | 50–150 ms | 国内 RTT + TLS 复用连接 |
| 后端处理 | < 5 ms | 内存房间表 + 唤醒 Event |
| 后端 → B（长轮询唤醒） | **≈ 0 ms**（唤醒即返回） | 关键：B 的长轮询正挂着，`asyncio.Event.set()` 立刻唤醒 |
| B 渲染 | 0 ms（下一帧） | |
| **端到端（理想）** | **≈ 100–250 ms** | 与"游戏内标点"的体感一致 |
| **端到端（最坏，B 的长轮询刚好超时重连）** | **≈ 20 s** | 长轮询窗口边界 + 重连耗时；协议 v1 的 `timeout=20` 是主因 |

**关键设计点**：长轮询的 20s **不是平均延迟**，而是"漏掉唤醒"时的最坏延迟。要压低最坏延迟：
1. 服务端收到新标点后**立刻** `Event.set()`（不能靠轮询循环 sleep）；
2. 客户端重连**立即**发起（不要等 1s 退避）；
3. 可选：把 `timeout` 降到 15s（代价是空转请求 +33%）。

**对比上游（服务端广播）**：<50 ms。我们的 100–250 ms 在"标点"这个场景里**完全可接受**（人类反应时间本身 ~200ms）。

### F.2 失败模式与降级

| 失败 | 检测 | 降级行为 | 玩家感知 |
|---|---|---|---|
| 后端 404/连不上 | `ApiException(network_error)` / HTTP 5xx | 状态 → `DEGRADED_LOCAL`，标点只本地渲染 | Toast 提示一次"仅本地可见"（26.3 无客户端聊天栏 API，见 §E.4） |
| 未认证 / 离线账号 | `no_token` / `no_session` | 同上（离线账号**永远**走这条） | 设置界面显示"当前离线，标点不同步" |
| token 过期 | 401 `unauthorized`/`bad_token` | 自动重认证一次；仍失败 → 降级 | 无感（首次）/ 提示（失败） |
| 熔断打开 | `circuit_open` | 降级 + 后台 30s 后自动恢复 | 无感 |
| 发送被限流 | 429 `rate_limited` | **本地照常显示**，不重试 | Toast 提示"标点太频繁" |
| 房间满 | 429 `room_full` | 本地照常显示 | 提示"当前标点太多" |
| 坐标越界 | 400 `bad_request` | 不重试、记日志 | 无（我们自己的坐标不该越界，属于 bug） |
| 长轮询断流 | 读超时 / 连接重置 | 立即重连（指数退避，上限 30s） | 无感 |
| 服务端时间漂移 | `serverTime` vs `clientTime` | 用 `serverTime` 校准本地偏移 | 无感 |

**降级铁律**：**本地标点功能永远可用**（纯客户端渲染），网络只影响"别人看不看得见"。这条必须在代码结构上保证——`core/PingRepository` 不依赖 `net/` 是否可用。

### F.3 隐私面

| 暴露面 | 内容 | 谁能看到 | 缓解 |
|---|---|---|---|
| **房间键可推导** | `roomId = sha256(服务器地址)[0:16]`；任何知道服务器地址 + 有有效 MC 账号的人都能订阅该房间 | 该服的玩家 + 任何知道地址的人 | ① 标点 TTL 20s；② 只有"当前在线于该服"的人才会去订阅（客户端逻辑）；③ v2 可加房间口令 |
| **坐标暴露** | 玩家精确坐标 | 同房间所有人 | ① 可选"模糊坐标"（4 格取整）；② 只在自己主动标点时才发 |
| **UUID/名字暴露** | `player.uuid` / `player.name` | 同房间所有人 | 已是公开信息（MC 服务器本来就有玩家列表） |
| **token 泄露** | `session.json` 里的 Bearer token | 本机其他进程 | ① 文件权限 `rw-------`；② 24h 过期；③ 只发 https |
| **后端可见** | 全部标点 + 时间 + 来源 IP | 后端运维 | ① 纯内存、不落库、不记日志（**必须在实现里强制**）；② 房间 5 分钟回收 |
| **第三方可见** | 无（不经过第三方） | — | 方案 A 的优势 |

⚠️ **必须写进代码约束**：后端 `ping.py` **不得**把坐标写进日志/数据库。这是与"方案 C 借道聊天"的关键区别（聊天会把坐标永久写进服务器日志）。

### F.4 跨维度与跨服

| 场景 | 行为 | 依据 |
|---|---|---|
| 同服不同维度 | **共用房间**，客户端按 `dimension` 字段过滤 | 协议 v1 §3 |
| 维度切换 | 停止渲染旧维度标点；**不重建房间、不重认证** | 协议 v1 §7.4 |
| 换服 | 重新算 `roomId`、重置 `since=0`、清空他人标点、旧长轮询 abort | 协议 v1 §7.4 |
| 换服但地址相同（BungeeCord 子服） | **会串**（同一地址 = 同一房间） | ⚠️ 已知限制，见 `实现方案.md §12.6` |
| 单机 / 局域网 | `roomId = sha256("singleplayer"\|"lan")` → **所有单机玩家共用一个房间** | ⚠️ 隐私问题：单机玩家会看到别人的标点。**建议 v1 单机直接禁用同步**（只本地） |
| 离线账号 | 无法认证 → 永远降级本地 | `FashionAuth.java:148-151`（`no_token`） |

### F.5 并发 / 容量上限

| 项 | 协议 v1 值 | 现实评估 |
|---|---|---|
| 每房间存活标点 | 200 | 20s TTL + 5 条/3s 限流 → 单房间理论峰值 33 条/秒，200 条上限够 |
| 长轮询等待者/房间 | 200 | **这是最大的资源风险**：200 个并发 HTTP 连接/房间 |
| 全局房间数 | 5000 | 5000 × 200 = 100 万并发连接 → **不可能** |
| 后端 worker | **1**（`config.prod.yaml:5`） | 单进程 asyncio 扛不住 10 万连接 |

**现实容量估算**（单 worker，asyncio，20s 长轮询）：
- 每个挂起的长轮询 ≈ 一个 `asyncio.Task` + 少量内存（~2 KB）→ 1 万并发 ≈ 20 MB，**CPU 几乎为 0**（都在 await）；
- 真正的瓶颈是 **文件描述符**（`ulimit -n`，通常 65535）和 **nginx worker_connections**（默认 1024/worker）；
- 结论：**单 worker 撑 5000–8000 并发长轮询是现实的**，对应约 25–40 个满员房间。

**建议**（写进 `实现方案.md`）：
1. 全局长轮询并发上限（默认 5000），超了直接返回 `503 + Retry-After`；
2. 每房间等待者上限从 200 降到 **64**（一个 MC 服 64 个装了 mod 的玩家同时标点已经很多了）；
3. 房间空闲回收从 5 分钟降到 **60 秒**（标点 TTL 才 20s，房间没必要活 5 分钟）；
4. 全局房间数上限 5000 → **1000**；
5. 加 `GET /api/ping/health` 暴露 `rooms` / `waiters` 计数。

### F.6 其它风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **认证调用 `session/minecraft/join` 会覆盖当前服务器登录的 serverId** | 每次进服认证都会调一次 join | ① 只在 `JOIN` 事件后调用（此时登录已完成）；② VMFashion 已用同样方式跑生产，未见踢人；③ 失败不阻断游戏 |
| **服务器地址归一化不一致** | `example.com` vs `example.com:25565` vs 大写 | 协议 v1 §3 已规定：小写 + 补默认端口。**必须单测覆盖** |
| **协议演进** | 后端先上线/客户端先上线 | `X-VMPing-Version` + 服务端宽松解析；v1 不做强校验 |
| **上游 MIT 许可** | 借鉴了算法与结构 | 保留版权声明 + `THIRD_PARTY_NOTICES.md`，见 `上游参考.md §4` |
| **Mod Menu 可选依赖** | 骨架已声明 `compileOnly` | 保持可选，不装也能用 |
