## 2. 接口清单

Base URL：`https://<host>/api/ping`（客户端可配置，默认 `https://www.venusyu045.cn/api/ping`）。
除认证两个接口外都要 `Authorization: Bearer <token>`（token `aud="ping"`）。
请求/响应均为 UTF-8 JSON。

| 方法 | 路径 | 鉴权 | 成功 | 说明 |
|---|---|---|---|---|
| POST | `/auth/challenge` | 无 | 200 | 申请一次性 `serverId`（TTL 120s，绑定来源 IP） |
| POST | `/auth/verify` | 无 | 200 | 反查 `hasJoined` 后签发 ping token（24h） |
| POST | `/rooms/{roomId}/pings` | Bearer | **201** | 发送标点 |
| GET | `/rooms/{roomId}/pings?since=&timeout=&dimension=` | Bearer | 200 | 长轮询拉取（最多等 25s） |

### 2.1 `POST /auth/challenge`

请求：

```json
{"mcUuid": "069a79f4-44e9-4726-a5be-fca90e38aaf5", "mcName": "Notch", "authServer": ""}
```

响应 `200`：

```json
{"serverId": "1f3c...", "expiresIn": 120, "authType": "mojang"}
```

- `authServer`：皮肤站（authlib-injector / Yggdrasil）base；正版留空。**只有配置白名单内**的地址才会被采用（防 SSRF），白名单外的地址被忽略（按 yggdrasil 处理，只用配置里的 bases）。
- 挑战表与 VMFashion **共用**（同一份 `core/fashion_auth.py` 内存表），但记录用途 `ping`：该 `serverId` 只能在本组 `/verify` 消费。
- 限流：同一来源 IP **20 次 / 60s**，超出 429 `rate_limited`（带 `Retry-After`）。

### 2.2 `POST /auth/verify`

请求：

```json
{"mcUuid": "...", "mcName": "...", "authServer": "", "serverId": "1f3c..."}
```

响应 `200`：

```json
{"token": "<JWT>", "expiresAt": 1730086400000, "mcUuid": "...", "mcName": "...", "authType": "mojang"}
```

- `expiresAt` 是**毫秒时间戳**（不是剩余秒数）。
- 后端 `GET .../hasJoined?username=&serverId=` 反查并**比对 UUID**，一致才签发。
- token：JWT HS256，`aud="ping"`、`typ="ping"`、`sub=mcUuid`（中继不需要身份表，**不落库**）。
- 失败码沿用 `fashion_auth` 的细分 code（见 §7）。

### 2.3 `POST /rooms/{roomId}/pings`

请求：

```json
{
  "dimension": "minecraft:overworld",
  "x": 123.45, "y": 64.0, "z": -89.25,
  "kind": "default",
  "targetUuid": "069a79f4-...",
  "targetName": "Notch",
  "clientTime": 1730000000123
}
```

响应 `201`：

```json
{"id": "9f2c...", "seq": 42, "serverTime": 1730000000200, "expiresAt": 1730000020200}
```

参数校验（失败 → 400 `bad_request`）：

| 字段 | 规则 |
|---|---|
| `roomId` | `[a-f0-9]{16}`（大小写不敏感，服务端转小写） |
| `dimension` | 非空，长度 ≤ 128 |
| `x` / `z` | 有限浮点（拒绝 NaN/Inf），`|x|,|z| ≤ 3e7` |
| `y` | 有限浮点，`|y| ≤ 2048` |
| `kind` | 白名单 `default` / `danger` / `item` / `go` / `help` |
| `targetUuid` | 可空；非空时必须是合法 UUID（统一规范化为带连字符小写） |
| `targetName` | 可空；长度 ≤ 64 |
| `clientTime` | 可选，**只记日志**；服务端时间才是准 |

其它错误：每玩家限流 429 `rate_limited`（带 `Retry-After` 秒）；房间满 / 全局房间数满 429 `room_full`。
可选请求头 `X-VMPing-Version`：只写 debug 日志，不做版本强校验。

### 2.4 `GET /rooms/{roomId}/pings`

查询参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `since` | `0` | 只返回 `seq > since` 的存活标点；负数按 0 处理 |
| `timeout` | `20` | 最多等待秒数，夹到 `[0, 25]`；`0` = 立即返回 |
| `dimension` | 无 | 可选过滤（不同维度共用同一房间） |

响应 `200`：

```json
{
  "seq": 45,
  "serverTime": 1730000001000,
  "pings": [
    {
      "seq": 43, "id": "9f2c...",
      "player": {"uuid": "...", "name": "Notch"},
      "dimension": "minecraft:overworld",
      "x": 123.45, "y": 64.0, "z": -89.25,
      "kind": "default",
      "targetUuid": null, "targetName": null,
      "serverTime": 1730000000200, "expiresAt": 1730000020200
    }
  ]
}
```

- 返回的 `seq` 是**房间当前最大序号**（可能是别的维度/过期前的），客户端下次用它做 `since`。
- 等待期间只有「别的维度」的新标点时会继续等剩余时间（不是立刻返回空）。
- 同房间等待者上限 64，**超出立即返回 `200` 空数组**（协议 v1.1 §6：不算失败，客户端按正常超时处理并立刻重试）；
  **全局长轮询并发上限 5000**，超出 `503 server_busy`（带 `Retry-After`）。
- 房间不存在时返回 `seq: 0, pings: []`（并会创建一个空房间等待，见 §4）。

### 2.5 错误体

统一：

```json
{"detail": {"code": "bad_request", "message": "x 不能是 NaN/Inf"}}
```

| code | HTTP | 触发 |
|---|---|---|
| `unauthorized` | 401 | 缺 `Authorization` 头 |
| `bad_token` | 401 | token 签名错 / 过期 / 受众不是 `ping` |
| `bad_request` | 400 | 参数越界（坐标 NaN/Inf、kind 未知、维度过长、roomId 非法…） |
| `rate_limited` | 429 | 发送太频繁 / challenge 太频繁（带 `Retry-After`） |
| `room_full` | 429 | 房间标点满 / 全局房间数满（**不含**订阅者满，见 §2.4） |
| `server_busy` | 503 | 全局长轮询并发打满（`VMT_PING__MAX_WAITERS_TOTAL`）；带 `Retry-After`，客户端按 `server_error` 退避 |
| `server_error` | 500 | 服务端未配置 JWT 密钥等内部错误 |

## 3. 鉴权（与 VMFashion 同构）

1. `POST /auth/challenge` → 拿 `serverId`（一次性、TTL 120s、绑定来源 IP）。
2. 客户端**直接**调会话服务器 `POST <sessionServer>/session/minecraft/join`（不经后端）。
3. `POST /auth/verify` → 后端 `hasJoined` 反查 → 比对 UUID → 签发 `aud="ping"` 的 JWT。

要点：

- **不复制**认证逻辑：直接复用 `core/fashion_auth.py` 的挑战表、`hasJoined` 校验、JWT 签发/校验，只是 `audience="ping"`。
- **用途隔离**：`Challenge.audience` 记录用途，ping 的 `serverId` 不能换 fashion token，反之亦然（都返回 403 `challenge_mismatch`）。
- **受众隔离**：fashion token（`aud="fashion"`）调 ping 接口 → 401 `bad_token`；ping token 调时装接口同理。
- 中继**不查数据库**：ping token 的 `sub` 就是 `mcUuid`，`mcName` 从 claims 取。

## 4. 房间与容量

房间 = 「服务器 × 维度」的临时空间（`roomId = hex(sha256(归一化服务器地址))[0:16]`，客户端计算，服务端只当不透明键）。**纯内存**，不落库、不迁移。

```
rooms: dict[roomId] -> _Room{
    seq: int,                        # 房间内单调递增，发送 +1（房间回收后归零）
    pings: deque[Ping] (maxlen=200), # 环形缓冲
    waiters: set[_Waiter],           # 本房间长轮询等待者
    last_active: float,              # 空闲回收用
}
waiters_total: set[_Waiter]          # 全局等待者集合（跨房间，全局并发上限用）
```

| 项 | 默认 | 行为 |
|---|---|---|
| 每房间存活标点 | 200 | 满了 429 `room_full`；过期条目先惰性清掉 |
| 标点 TTL | 20s | 惰性清理（房间被访问时才扫 deque 左端） |
| 房间空闲回收 | **60s** | 无活动且**无等待者**才回收（房间重建后 `seq` 归零，见下） |
| 全局房间数 | **1000** | 超限先回收空闲房间，仍超限 429 `room_full` |
| 每房间等待者 | **64** | 超出**立即返回 200 空数组**（协议 v1.1 §6，不是错误） |
| **全局长轮询并发** | **5000** | 跨房间总等待者数，超出 503 `server_busy`（带 `Retry-After`） |
| 每玩家发送 | 5 条 / 3s | 滑动窗口（按 `mcUuid`），超出 429 `rate_limited` |

> 默认值是按**单进程部署**（`backend/config/config.prod.yaml` 的 `workers: 1`）拍定的：
> 一个长轮询等待者 = 一个挂起中的 HTTP 连接，单进程必须给房间级 + 全局级两层硬上限，
> 否则恶意/异常客户端能把文件描述符与内存吃满。全部可用 `VMT_PING__*` 覆盖。

### 4.1 `seq` 语义（房间回收 → 归零，**不是**全局单调）

`seq` 是**房间内**单调递增序号（每发一条 +1），房间被空闲回收后**连同 `seq` 一起消失**：

- 房间重建后 `seq` 从 `0` 重新开始，第一条标点 `seq = 1`（**绝不**复用旧 `seq`）；
- `GET` 一个不存在的房间（刚被回收 / 从没人发过）返回 `{"seq": 0, "pings": []}`；
- 客户端约定：收到 `seq < 本地 lastSeq` → 判定「房间被回收」，**重置游标**并清空他人标点；
- 所以服务端**不能**改成「全局单调 seq」：那会让客户端永远等不到新标点（`since` 比新房间的 `seq` 大）。

对应单测：`tests/test_ping_relay.py::TestRoomLifecycle::test_reclaimed_room_seq_restarts_from_zero`、
`::test_idle_room_is_reclaimed_and_seq_restarts`。

并发模型：

- 单进程、状态用 `threading.RLock` 保护。临界区只有纯内存 O(1)/O(n≤200) 操作，**没有 I/O 与 await**，不会阻塞事件循环；同时覆盖「FastAPI 把同步路由丢线程池」的路径。
- 长轮询用 `asyncio.Event` **事件驱动**唤醒（不是短轮询）：同 loop 直接 `set()`，跨线程走 `loop.call_soon_threadsafe`。注册等待者后会再查一次，避免「注册前 publish」的丢唤醒竞态。
- `asyncio.Lock` 刻意不用：`asyncio.run()` 每次新建 loop，模块级锁绑定到已关闭 loop 会抛 `bound to a different event loop`（离线单测与多事件循环场景不安全）。

## 5. 配置项

环境变量（前缀 `VMT_`，嵌套分隔 `__`），全部可选。默认值 = 协议 §6 的容量，
其中房间/等待者类默认值按**单进程部署**收紧（见 §4 的说明）：

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `VMT_PING__ENABLED` | `true` | 总开关；关闭后不挂载 `/api/ping` 路由 |
| `VMT_PING__MAX_PINGS_PER_ROOM` | `200` | 每房间存活标点上限 |
| `VMT_PING__PING_TTL_SECONDS` | `20` | 标点 TTL（秒） |
| `VMT_PING__ROOM_IDLE_SECONDS` | `60` | 房间空闲回收（秒）；回收后房间 `seq` 归零 |
| `VMT_PING__MAX_ROOMS` | `1000` | 全局房间数上限 |
| `VMT_PING__MAX_WAITERS_PER_ROOM` | `64` | 每房间长轮询等待者上限 |
| `VMT_PING__MAX_WAITERS_TOTAL` | `5000` | **全局长轮询并发上限**（跨房间，超出 503 `server_busy`） |
| `VMT_PING__RATE_LIMIT` | `5` | 每玩家发送条数 |
| `VMT_PING__RATE_WINDOW_SECONDS` | `3` | 每玩家限流窗口（秒） |
| `VMT_PING__CHALLENGE_RATE_LIMIT` | `20` | 认证 challenge 每 IP 次数 |
| `VMT_PING__CHALLENGE_RATE_WINDOW_SECONDS` | `60` | challenge 限流窗口（秒） |
| `VMT_PING__WAIT_TIMEOUT_SECONDS` | `20` | 长轮询默认等待（秒） |
| `VMT_PING__MAX_WAIT_TIMEOUT_SECONDS` | `25` | 长轮询等待上限（秒） |
| `VMT_PING__TOKEN_TTL_SECONDS` | `86400` | ping token 有效期（秒） |

认证外呼（`hasJoined`）复用 fashion 的配置：`VMT_FASHION__YGGDRASIL_BASES`、
`VMT_FASHION__MOJANG_SESSION_SERVER`、`VMT_FASHION__CHALLENGE_TTL_SECONDS`、
`VMT_FASHION__HTTP_TIMEOUT_SECONDS`。**上线新皮肤站必须先加白名单**，否则该站玩家 verify 会 `not_joined`。

改配置需要**重启进程**（中继是进程内单例，首次请求时按配置构造）。

## 6. 部署注意

1. **必须单 worker**。中继是进程内内存：`uvicorn --workers 2+` / gunicorn 多进程会让同一房间的玩家落到不同进程，互相收不到标点（表现为「有时能收到、有时收不到」）。
   现有 `deploy/systemd/vmtools-next.service` 与 `deploy/Dockerfile` 都是单进程启动，保持不变即可。
2. **反向代理超时要够长**：长轮询最长 25s。现有 `deploy/nginx/vmtools-next.conf` 的
   `location /api/ { proxy_read_timeout 300s; }` 已足够；若改小到 <30s 会截断长轮询（客户端会立刻重连，功能不坏但请求量翻倍）。
3. **重启即丢房间**：标点与房间都不持久化。重启后客户端下一次 `since=0` 会拿到空数组并自动继续，无需运维干预。
4. **内存估算（风险点）**：理论上限 = `MAX_ROOMS × MAX_PINGS_PER_ROOM` = 1000 × 200 = 20 万条标点，
   按每条 0.4–0.8KB 估算约 **80–160MB**（真实负载远低于此：TTL 只有 20s、每玩家 5 条/3s）。
   内存紧张时优先调小 `VMT_PING__MAX_ROOMS`（按实际活跃服务器数量给，通常 50–200 足够）；
   长连接压力看 `VMT_PING__MAX_WAITERS_TOTAL`（一个等待者占一个挂起连接 + 一个 `asyncio.Event`）。
5. **反代必须转发** `Authorization`（默认转发）与 `X-VMPing-Version`（仅日志用，不转发也不影响功能）。
6. **来源 IP**：challenge 绑定来源 IP，依赖 `X-Forwarded-For`（uvicorn `forwarded_allow_ips`）。后端端口**不能**直接暴露公网，否则可伪造 IP 绕过认证限流（与 fashion 同一风险，见 nginx 配置顶部注释）。
7. **时钟**：`serverTime` / `expiresAt` 用服务端 `time.time()`（UTC 毫秒），与容器时区无关；宿主机需有 NTP，客户端只信服务端时间。
8. **可观测性**：`core/ping_relay.py` 提供 `stats()`（房间/标点/等待者数）与 `prune()`，目前未挂 HTTP 端点；
   需要时可在运维脚本里通过进程内探针或后续加只读管理端点（协议 v1 未定义，属扩展）。
9. **多副本 / 负载均衡**：v1 明确不支持（纯内存、无跨进程同步）。要横向扩展需换成 Redis 之类的共享存储，属 v2 议题。

## 7. 与协议 v1 的差异 / 补充约定

1. **认证接口的细分错误码**：`/auth/*` 沿用 `fashion_auth` 的 code（`invalid_uuid`、`invalid_mc_name`、`challenge_not_found`、`challenge_expired`、`challenge_mismatch`、`source_mismatch`、`not_joined`、`uuid_mismatch`、`upstream_unavailable`），HTTP 状态落在 400/401/403/503。协议 §1 的表格只列了 6 个通用码，客户端按**状态码**降级即可（非 2xx 一律降级本地标点）。
2. **请求体类型错误是 422**：例如 `"x": "abc"`、缺 `dimension` 字段，由 FastAPI/pydantic 直接返回 422（协议未定义 422）。客户端应把 422 当 `bad_request` 处理、不重试。
3. **`dimension` 发送时不能为空**（`""` → 400）；GET 的 `dimension` 过滤参数为空串时按「不过滤」处理。
4. **`roomId` 大小写不敏感**：服务端统一转小写后再校验；大写/混合大小写的 hex 也能用（客户端正常只会发小写）。
5. **`targetUuid` 会被规范化**：32 位无连字符 / 大写 UUID 都接受，存成带连字符小写。
6. **房间不存在时 GET** 会创建空房间并等待（避免客户端空转轮询）；该房间同样计入 `MAX_ROOMS`、同样按 `ROOM_IDLE_SECONDS`（默认 60s）空闲回收，回收后 `seq` 归零（见 §4.1）。
7. **429 / 503 一律带 `Retry-After`**（秒，≥1）；`room_full` 的 `Retry-After` 是建议重试间隔（1–5s），客户端也可直接用本地退避。
   **例外**：每房间等待者超限不返回错误，而是 `200` + 空数组（协议 v1.1 §6），客户端把它当「正常超时」立刻重试即可。
8. **`server_busy`（503）是实现补充的错误码**（协议 §1 未列）：全局长轮询并发打满时返回，
   客户端按 `server_error` 处理（退避重试），**不要**当成 `room_full` 或认证失败。
9. **`seq` 是房间内序号，房间回收后归零**（见 §4.1）：客户端必须用「`seq` 变小」判定房间重建，
   服务端不会、也不应该把它做成全局单调。

覆盖点：

- `test_ping_relay.py`：房间键规范化、TTL 惰性清理、环形缓冲上限 / `room_full`、限流窗口与 `Retry-After`、长轮询超时/唤醒/维度过滤/等待者上限（房间满→空数组）/取消、丢唤醒竞态、房间空闲回收与 `seq` 归零、全局房间数上限、**全局长轮询上限 → 503 `server_busy`**、坐标/kind/维度/名称校验。
- `test_ping_api.py`：鉴权 401（缺 token / 无效 token / fashion token）、参数 400、限流 429（`Retry-After`）、房间满 429、发送 201 形状、长轮询唤醒、**全局并发满 503 `server_busy`**、challenge→verify 全流程（假 `hasJoined`）、用途隔离（ping 挑战不能换 fashion token）、配置兜底。
- `test_ping_http.py`：真实 HTTP 下的 401/201/200/429 形状与 `Retry-After` 头、`targetUuid`/`player` 序列化；路由表断言 4 个端点挂在 `/api/ping` 下。

> 本机（离线环境）没有 `fastapi`/`httpx`，`TestClient` 不可用：`TestPingHttp` 全部 skip，
> `TestPingRouteTable` 用 stub 路由表照常执行。装了依赖的机器 / CI 上会真正跑 HTTP 用例。
